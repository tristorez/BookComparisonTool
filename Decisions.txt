Real-time NFL odds board, DraftKings vs FanDuel (Betstamp take-home): the decision log
====================================================================================================

PURPOSE
  The assignment PDF, Key Concept 1: "We will ask you to defend each choice."
  This file is that defence, written down. For every decision it gives the problem, what we chose,
  what we rejected and the concrete reason it lost, the evidence and its source, what the choice
  costs, and what would change our mind. The README links here, and code comments cite entries
  by ID (src/shared/wire.ts cites D-07 and D-21, src/server/feedMerge.ts D-35).

HOW TO READ IT
  - Start with the INDEX: it maps each section of the PDF to the decisions that answer it.
  - Then one block per decision, D-01 to D-41, in ID order. IDs are stable and never reused.
  - Block fields:
      Status        state and date (legend below) | PDF section it answers | Owner
      Context       the problem and its constraints
      Decision      what we do
      Alternatives  what we weighed, each with the reason it lost
      Evidence      measurements and tests, each with its source
      Trade-offs    what the decision costs
      Revisit if    the evidence that would change it
      Where         code paths, README sections, docs. "(planned)" marks a path from the plan's
                    repo layout that is not written yet.
  - Evidence sources: "README <section or issue id>" is README.md in this repo; "plan" is the
    approved implementation plan; "measured 2026-10-19 on Box A" was taken that day on the AWS
    host; a repo path (e.g. test/replay.test.ts) means the figure is in that file. No number
    here is a projection unless it is labelled as an expectation or an estimate.
  - Owners: "user" is the user's call; "user + Claude" is the user's call, refined with Claude;
    "Claude (plan)" comes from the approved plan; "Claude (build)" was settled while building,
    within the plan; "reviews" means shaped by the independent design review (a Claude Plan
    agent) and/or the external Codex review; "ingestion session" is the session that built the
    book connectors.
  - Entries are never deleted. A replaced entry is marked "Superseded by D-xx" and kept. The file
    is updated at the end of every implementation phase (plan Phases 0-7).

STATUS LEGEND
  Accepted          Decided and in force; the evidence cited is in hand.
  Proposed          Suggested, not yet signed off by the user.
  Superseded        Replaced by the entry named; kept for the record.
  Pending evidence  Decided, but a supporting measurement has not been taken yet. The Evidence
                    field names the phase that will produce it and the method.
  Statuses combine, e.g. "Accepted 2026-10-19; Pending evidence (Phase 6)".

TERMS
  Box A       AWS t3.medium in us-east-2b with an Elastic IP: board, website, feed A, builds, and
              every run that needs DraftKings.
  Box B       AWS t3.micro in us-east-2b: feed B only, streamed to Box A over private TCP 7070.
  Feed        One box's ingestion of every book (one connector per book per box).
  First copy  The earliest report of a new price state from any feed; the board keeps that one.

  bt / rx     The book's own change timestamp (DK createdTime in ms; FD PIR updatedAt in whole

D-04  Latency measurement model: book -> backend -> browser, per book, pregame and live
Status: Accepted 2026-10-19; Pending evidence (Phase 6) | PDF: Key Concept 1 | Owner: Claude (plan)
Context:      The PDF's main question: "how old is the number on the screen?", end to end, per
              book, pregame and live, across three clocks: the book's, our boxes', the viewer's.
Decision:     Every quote carries bt, rx, the first channel and the first feed. Per-channel
              `sample` events (before cross-channel dedupe) time each channel without bias
              toward the winner, and DK's createdTime / publishedTime / websocketPublishTimestamp
              split DK's leg into engine, pipeline and gateway. Legs: book -> box = rx - bt;
              box -> board = flush - rx; board -> browser and book -> browser via the page's
              estimate of the server clock (min-RTT offset from 5 x /api/time, refreshed every
              5 min; each beacon carries its error bound, +/- RTT/2, and the server keeps their
              distribution as the browserClockError series); paint = receive to the next
              animation frame. Beacons every 15 s (at most 300 samples) go to POST
              /api/latency. Reservoirs per book x phase x channel x feed give p50/p90/p99/n and
              the skew floor min(rx - bt); snapshots, resumes and hidden tabs are excluded. DK
              reconcile corrections are logged (3 or more trigger a resubscribe); a "missed by
              push" counter is not built yet.
Alternatives: - Server-side only (rx - bt): rejected; it omits the browser leg the PDF asks for.
              - Browser age against the browser's own clock: rejected; a viewer's clock error is
                unknown and can swamp the signal. The offset method bounds it.
Evidence:     Box clocks: Amazon Time Sync; chrony on 2026-10-19: Box A 0.95 us fast, Box B 1.0 us
              slow (README Latency). First per-channel readings in production (/api/metrics,
              DK pregame, n = 27 per box, 2026-10-19): DK gateway -> box p50 15-17 ms; DK
              engine -> publish p50 20-21 ms but p90 1.2-1.3 s (inside DK); Box B's copy p50
              55 ms behind the first. End-to-end per book x pregame/live: Pending evidence
              (Phase 6). scripts/measure-e2e.ts runs through WAS@SF (Mon 10/19, 8:15 pm ET;
              00:00-03:40 UTC) from the St. Louis dev VPS into docs/latency/, saving
              /api/metrics every 15 min; a run from Canada (as reviewers) needs the user.
              Later windows: Thu 10/22 NE@CHI, Sun 10/25 full slate, Mon 10/26 DAL@PHI.
Trade-offs:   Book clocks are not ours, and FD's has whole-second resolution (D-05). Poll-first
              FD quotes carry no bt, so they report backend -> browser plus a bound.
Revisit if:   The clock-offset error (+/- RTT/2) nears the legs being measured.
Where:        src/server/latency.ts, web/src/lib/clock.ts, web/src/lib/latency.ts,
              scripts/measure-e2e.ts; src/shared/wire.ts (LatencySample); docs/latency/.

D-05  FanDuel precision rule: raw age is reported as an upper bound
Status: Accepted 2026-10-19 | PDF: Key Concept 1 | Owner: Claude + reviews
Context:      FD's only book timestamp, PIR updatedAt, has whole-second resolution (truncated). A
              change late in a second is stamped at the start of that second, so raw age
              overstates the true age by up to 1 s.
Decision:     The true FD book -> X latency lies in (raw - 1 s, raw]. Raw is reported as an
              upper bound, with that interval, everywhere (README, docs/latency/, /api/metrics).
              A midpoint figure appears only labelled "estimate (truncation-corrected)". DK
              createdTime is in ms and needs no such rule.
Alternatives: - Report the midpoint as the result: rejected. It assumes changes are spread evenly
                within the second, so it is an estimate, not a measurement. The README's
                "~0.5 s typical" is labelled as an estimate for this reason.
              - Leave FD out of book-side latency: rejected; the bound is still informative.
Evidence:     PIR push age at receipt, raw p10/p50/p90 (README Latency): St. Louis, 180 s, 143
              markets: 586/1035/1492 ms; Ohio (Box A), 120 s, 70 live markets: 524/964/1373 ms.
              Under this rule the St. Louis p50 is at most 1035 ms, true value in (35, 1035] ms.
              NFL pregame/live and book -> browser: Pending evidence (Phase 6).
Trade-offs:   FD rows look worse than DK rows at equal true latency; the README says why.
Revisit if:   FD exposes a sub-second timestamp on either channel.
Where:        src/server/latency.ts; README "Latency: measured so far", FD-5.

D-06  Browser transport: Server-Sent Events, not WebSockets
Status: Accepted 2026-10-19 | PDF: Key Concept 1 | Owner: user
Context:      Updates must reach the browser on their own. Traffic is one-way, server ->
              browser; the only upstream traffic is a periodic latency beacon.
Decision:     SSE: GET /api/stream (text/event-stream) through Caddy over HTTP/2 (D-11).
              Beacons are plain POSTs (sendBeacon to /api/latency).
Alternatives: - WebSocket: rejected. Latency is the same, since both write a frame to an open TCP
                connection. WebSocket buys two-way messaging we don't use and gives up what SSE
                has built in: automatic reconnect with Last-Event-ID resume (D-07), plain HTTP
                through the proxy (no upgrade), and HTTP/2 multiplexing of many tabs on one
                connection.
              - Browser polling: rejected; it adds up to a full interval of age to every update.
              - A hosted pub/sub service: rejected; a third party and an extra hop inside the
                very path we are measuring.
Evidence:     Stack decision (plan, "Decisions locked with the user"); it supersedes an earlier
              README draft that planned WebSocket push. SSE behaviour through the edge: Pending
              evidence (Phase 5), checks listed in D-11.
Trade-offs:   EventSource cannot set headers, so resume uses Last-Event-ID or ?since= (D-07).
              Browsers cap HTTP/1.1 connections per origin, so HTTP/2 is required (D-11).
Revisit if:   Viewers need to send per-update messages (e.g. subscribe to a subset of games), or
              a proxy in the path buffers SSE.
Where:        src/server/sse.ts, web/src/lib/stream.ts, src/shared/wire.ts; README "Serving the
              board: Server-Sent Events".

D-07  Stream protocol: snapshot then deltas, <boot>.<seq> ids, sequence invariants
Status: Accepted 2026-10-19 | PDF: Key Concept 1 | Owner: Claude + reviews
Context:      Browsers join mid-stream, reconnect after blips and must survive a server restart
              without ever applying a delta to the wrong base state.
Decision:     - Connect: one snapshot, then deltas. Event ids are <boot>.<seq> (boot is random
                per process start); resume via Last-Event-ID or ?since=. A snapshot replaces the
                replay when the boot differs, seq is ahead of head or older than the ring tail
                (2,000 deltas), or the replay would be bigger; built and attached in one turn.
              - Invariants: (1) seq counts emitted deltas only, consecutive, never skipped;
                (2) snapshot or replay first, then live deltas, heartbeats interleaved; (3) hb.seq
                is never ahead of the deltas written on that connection (deltas go out in their
                flush, heartbeats from a timer); (4) a heartbeat follows every replay. Heartbeat
                {boot, seq, ts, status} on connect, then every 5 s.
              - Client: apply a delta only if seq = lastApplied + 1; ignore duplicates and older
                ones; a gap -> resume; new boot -> resync; hb.seq > lastApplied -> a gap, resume;
                12 s without a frame -> reconnect with ?since= (backoff 1 s to 15 s). While
                disconnected, the board shows stale.
Alternatives: - Plain integer ids: rejected. After a restart seq starts over, and a client could
                "resume" into another process's history; the boot prefix rules that out.
              - Heartbeats without seq: rejected; a lost delta would hide until that cell moved.
              - A snapshot on every reconnect: rejected; wasteful when the ring holds the gap.
Evidence:     Ids and invariants came from the design and Codex reviews. test/integration.test.ts
              (real sockets): snapshot then consecutive deltas with heartbeats never ahead;
              resume via Last-Event-ID and ?since=; a different boot gets a snapshot. Through
              the edge: Pending evidence (Phase 5, D-11).
Trade-offs:   The ring costs memory; a client gone for more than 2,000 deltas gets a snapshot.
Revisit if:   Resume-vs-snapshot counts in /api/metrics show the ring too short on a full slate.
Where:        src/shared/wire.ts (the contract), src/server/sse.ts, src/server/board.ts,
              web/src/lib/stream.ts; README "Serving the board: Server-Sent Events".

D-08  Coalesce per event-loop turn; never batch on a timer
Status: Accepted 2026-10-19 | PDF: Key Concept 1 | Owner: Claude + reviews
Context:      The PDF asks about batching vs sending immediately. One book frame often changes
              several quotes at once, and each change can move the best price for both sides.
Decision:     Changes accumulate within one event-loop turn and flush via setImmediate as one
              delta, adding under 1 ms. Nothing is batched on a timer: connectors apply each
              frame immediately, and the feed link forwards each change immediately. A flush
              recomputes both sides of each affected (game, market) and emits only real
              changes, never an empty delta. Then seq++, stamp ts, push to the ring, broadcast.
Alternatives: - One event per quote change: rejected. A line move would reach browsers as
                half-applied states (one side moved, best not yet recomputed): visible
                inconsistency for no latency gain.
              - A fixed batching window: rejected. It adds up to a whole window of age to every
                update, to save bytes we don't need to save (D-09).
Evidence:     The connectors alone on Box A: event-loop lag p99 0.5 ms (README Hosting). Unit
              test: one
              event-loop turn -> one delta (test/board.test.ts). Board time (flush - rx) per
              book: Pending evidence (Phase 6).
Trade-offs:   A burst inside one turn becomes one larger delta.
Revisit if:   Profiling shows one turn's work stalling the loop.
Where:        src/server/board.ts; README "Serving the board: Server-Sent Events".

D-09  Payload: compact JSON, serialized once, no stream compression
Status: Accepted 2026-10-19; Pending evidence (Phase 6) | PDF: Key Concept 1 | Owner: Claude (plan)
Context:      The PDF asks about payload size, and the design must hold up with many viewers
              (Key Concept 5).
Decision:     - Deltas carry only what changed (quotes, bests, status) with short keys (bt, rx,
                ch, feed, prev). A snapshot goes out only on join, or when a replay would be
                bigger.
              - Each delta is serialized once, and the same string is written to every socket.
              - No compression on the SSE stream. @fastify/compress handles everything else;
                the Caddyfile has no `encode`.
              - Backpressure: a client with 1 MB unsent has its response destroyed; it resumes
                (D-07).
Alternatives: - Per-connection gzip of the stream: rejected. Deltas are small, a compressor per
                client costs CPU and memory at scale, and compressors buffer, which adds age.
              - Binary encoding (MessagePack, protobuf): rejected. It brings schema brittleness
                for a negligible saving, the same call as DK-3.
Evidence:     A one-market move is ~550 bytes (two quotes with previous prices, two best-price
              cells); the full snapshot is ~58 KB uncompressed for a 15-game slate (README
              Serving the board). Bytes per delta and per snapshot across live windows (SseHub
              counters lastDeltaBytes, maxDeltaBytes, lastSnapshotBytes): Pending evidence
              (Phase 6).
Trade-offs:   JSON is larger than binary on the wire, which doesn't matter at these sizes.
Revisit if:   Snapshots grow (more leagues, alt lines); then compress the snapshot event only.
Where:        src/server/sse.ts, src/server/app.ts, deploy/Caddyfile; src/shared/wire.ts;
              README "Serving the board: Server-Sent Events".

D-10  Hosting region: AWS us-east-2 (Ohio)
Status: Accepted 2026-10-19 | PDF: Key Concept 1 | Owner: user + Claude
Context:      FD's push service (AppSync) runs in us-east-2 per FD's own web config; its REST
              hosts sit behind CloudFront (from Ohio, PoP CMH68 Columbus; the origin answers
              "Cougar"). DK sits behind Akamai; its client config puts API gateways in GCP
              us-east4 (N. Virginia).
Decision:     Run both feed boxes and the board in AWS us-east-2b.
Alternatives: - us-east-1: rejected. It might be ~10 ms closer to DK but would be ~10 ms farther
                from FD, and both are dwarfed by the books' own publish delays.
              - The St. Louis dev VPS: rejected. Akamai blocks it on every DK host (DK-1), and
                every FD path is slower (below).
              - A free PaaS (the PDF suggests Fly.io, Render, Railway, Vercel): rejected. DK
                access depends on egress-IP reputation (D-14), so we need IPs we can probe and
                keep (an Elastic IP), long-lived sockets, and a region of our choosing.
Evidence:     Measured 2026-10-19, warm connections, AWS us-east-2b (the first test instance and
              Box A) vs St. Louis (README Hosting):
              - FD PIR connection_init -> connection_ack: 1.3-4.7 ms vs 26-62 ms
              - FD PIR GraphQL, warm time to first byte: 10-12 ms (CMH68) vs 57 ms (ORD58)
              - FD SMP round trip: ~12 ms vs 39 ms
              - DK subscribe -> subscribed: 35-63 ms vs blocked (403)
              - DK REST snapshot, cold incl. TLS: 130-220 ms (an earlier run: 193 ms) vs blocked

D-22  Fair-probability anchor: consensus no-vig, both sides scored against one anchor
Status: Accepted 2026-10-19 | PDF: Key Concept 4 | Owner: user + Claude
Context:      R3 needs P(win) and P(push) for each offer. The first version scored each offer
              with its own book's no-vig probability.
Decision:     A pluggable getFairProbability(game, market). The default, meanNoVig, is the mean
              of the qualifying books' multiplicative no-vig P(cover). Both sides of a spread are
              scored against the same anchor, so favourite and underdog picks stay consistent.
              - A book qualifies for a pregame spread when both sides are present, unsuspended
                and validly priced, the book isn't stale, home line = -away line, and the game
                isn't live. One qualifying book is enough, and offers needn't come from one.
                With none, the market falls back to R4.
              - Margin axis M = home - away; anchor = P(M > x) at a half-point x. A book at
                integer h gives x = -h + .5 with p * (1 - pm(-h)); at half-point h, x = -h with
                p. Books move to a common x through the push masses between, then average and
                clamp to [.001, .999].
Alternatives: - Scoring each offer with its own book's no-vig: rejected. R collapses to
                (1 - push)/overround + push, identical for both sides, so the same book wins
                both sides of every market. Verified numerically on the PDF example: DK .9586 vs
                FD .9565, on both sides.
              - A sharp-book or exchange anchor: unavailable with two books; the hook is ready.
Evidence:     The PDF example, completed with away prices: DK home -3 / away +3, both -110; FD
              home -3.5 +100 / away +3.5 -120; pm(3) = .09. Anchor P(M > 3.5) = .455 (DK), .478
              (FD), .467 (mean). Favourite: DK .981 vs FD .933. Underdog: FD .978 vs DK .936
              (plan Phase 1; test/bestPrice.test.ts).
Trade-offs:   With two books the consensus is thin, and one off-market book moves it. The
              cross-book sanity check (D-25) excludes grossly inconsistent games.
Revisit if:   A third book or a sharper reference arrives; swap the anchor function.
Where:        src/shared/bestPrice.ts (getFairProbability, bookAnchor, estimatedReturn);

D-23  NFL push table from nflverse, with empirical-Bayes shrinkage
Status: Accepted 2026-10-19 | PDF: Key Concept 4 | Owner: Claude (plan)

D-34  Feed link: NDJSON over private TCP with a token, snapshot resync, no buffering
Status: Accepted 2026-10-19 | PDF: Key Concept 5 | Owner: Claude (plan)

D-35  Cross-feed merge: first copy wins, ordered by when each state was in effect
Status: Accepted 2026-10-19 | PDF: Key Concept 1, 5 | Owner: Claude (build) + reviews
Context:      Two boxes, each with push, poll and snapshot channels, report the same book at
              different lags. "Last write wins" would let a slower stream roll a price back.
Decision:     A pure QuoteMerge per (book, quote key). Feeds are <box>:<channel> streams fed by
              the connectors' sample events; state = (american, line, suspended, live).
              - Each report gets an in-effect time: its book time, else its receive time minus
                the channel's staleness (poll 50 ms, push 1 s, snapshot 2 s). knownAt = the
                latest time the shown state is known to have held at the book.
              - Same state as shown: a confirmation (that feed's lag is recorded). In effect
                before knownAt: older, rejected. Otherwise: newer, shown (first copy wins).
              - FD pushes (whole seconds) are matched by position in the last 64 shown states: a
                re-report of an earlier occurrence is a late copy, rejected.
              - A feed repeating the state it last reported is another delivery of one
                observation (each box reports it as a sample and as a change; a resync re-sends
                it): a duplicate, never judged again.
              - Every 1 s: heal when every healthy feed has held one other state for 3 s; fail
                over when the shown value's feed turns unhealthy. A quote is removed only when no
                healthy feed lists it; if every feed is unhealthy, the last value stays, stale.
Alternatives: - Last write wins: rejected; rollbacks.
              - Blocking any value shown before (the plan's 15 s superseded set): removed. It
                delays genuine reversals in oscillating prices (also FD-7).
              - "This feed is in sync, accept its next change": removed. Polls make the board
                skip states, so value matching can't prove sync: 31-69 rollbacks in simulation.
              - Primary feed with fallback: rejected; it discards Box B's wins (D-33).
Evidence:     Simulation, 400 seeded runs with bursts and dropped push frames: 0 rollbacks, all
              converge; ~3% of FD states shown late (p50 224 / p90 524 ms) while an ambiguous
              push waits for a poll. Live FD replay (180 s, 70 in-play markets, 2,910 channel
              reports): 1,544 states, 0 flips, 633 of 1,378 shown before push delivered them
              (mean 274 ms earlier), 2 late (595 ms); push alone: 312 late (README The board;
              test/replay.test.ts). Drill with Box B's link held 2 s behind (D-40): before the
              repeat rule, 20 of 958 shown changes came from B, old prices put back (a late
              copy's second delivery passed when FD's whole-second times tied); after it, 0 of
              942. test/feedMerge.test.ts covers it; the replay numbers are unchanged.
Trade-offs:   A genuine revert first seen only by a lagging feed shows up to 3 s late (heal).
              A poll carries no book time, so a poll answered late from a stale replica looks
              like a genuine reversal and shows until the next on-time report (<= 0.5 s with
              staggered feeds; reproduced against QuoteMerge). SMP served 0 stale reads in 297
              differing observations (README Latency).
Revisit if:   /api/health shows heals or late copies piling up in live windows.
Where:        src/server/feedMerge.ts, src/server/board.ts; scripts/replay-merge.ts; README "The
              board: two feeds, one view".

D-39  Credentials that can change: FD keys re-read from the live bundle, DK anonymous-JWT fallback
Status: Accepted 2026-10-19 | PDF: Key Concept 3 | Owner: ingestion session
Context:      D-15 stands: no logins, cookies or sessions, and nothing expires. Two things could
              still change without warning: FD can rotate its public keys (_ak, PIR client key)
              with a deploy, and DK could start checking the socket jwt it ignores today. The PDF
              asks how the system recovers without a human.
Decision:     - FD: a rejected key is recognised by its exact signature. sbapi answers
                {"error":true} with 404 (board), 500 (in-play) or 400 (missing key); PIR answers
                connection_error UnauthorizedException (401). The connector then re-reads FD's
                live bundle (/sw.js -> /static/js/main.<hash>.js), extracts every candidate key,
                adopts the first one the live API accepts, and retries discovery or reconnects
                push at once. At most one re-read per 5 min (30 s after a failed download). SMP
                needs no key, so prices keep flowing at 1 s meanwhile (FD shown degraded, with
                the reason).
              - DK: two subscription refusals in a row (an error frame, an unsubscribe right after
                subscribing, or close 4000) switch the socket from "default-token" to DK's
                anonymous enterprise JWT (generateAnonymousEnterpriseJWT: no cookies, 120 s). It
                is sent in the URL and the subscribe, and renewed at 90% of its life with 3 tries
                2 s apart, as DK's own client does. A refusal in JWT mode fetches a fresh token
                before reconnecting; other reconnects reuse the current one. A refusal, a 4000
                close included, retries on the normal backoff with no floor, because the retry
                changes the token.
Alternatives: - Start DK on the JWT: rejected. DK's site sends "default-token", it works today,
                and the JWT adds a token request and a renewal loop for no gain while DK checks
                nothing. The fallback is one switch away.
              - Hard-coded keys and an alert for a human: rejected. The PDF asks for recovery
                without one, and the keys are public in a bundle we can read (FD-1).
              - A headless browser that picks up whatever the site uses: rejected (D-15). It is
                heavy, and it walks into PerimeterX on the HTML.
Evidence:     Measured 2026-10-19.
              - FD failure signatures: wrong _ak -> 404 {"error":true} (board), 500 (in-play);
                missing -> 400; wrong PIR key -> connection_error UnauthorizedException 401.
              - FD live run from St. Louis with both keys wrong: current keys adopted 0.95 s after
                start, push connected 0.17 s later, 15 games / 90 quotes live.
              - DK on Box A: "default-token", an anonymous JWT, a garbage string and no jwt were
                all subscribed. The connector in JWT mode fetched its token in 0.3 s and went
                live 410 ms after connecting (15 games, 90 quotes). Side by side for 25 s, a JWT
                socket and a default-token socket received identical frames (2 updates, 1
                selection change each).
              - DK mock that refuses "default-token": live again within 0.7 s of the first
                refusal. A 1011 close in JWT mode reconnected in 211 ms on the cached token.
              - DK's client code: getTokenRenewTimeout(e) = 1e3*(e-10*e/100), 3 tries 2 s apart;
                on a subscription error it refreshes the token and resubscribes
                (refreshTokenAndReInit); updateToken writes url.queryParams.jwt.
Trade-offs:   Learned keys live in memory: after a restart the first rejection repeats the refresh
              (about 1-2 s). The extractor depends on the bundle's shape (the key maps and the
              AppSync config); if FD restructures it, the refresh adopts nothing, the status says
              the key is rejected, and a human updates the pattern. The DK fallback is verified
              against a mock and in JWT mode live, but DK's real refusal format is unknown,
              because DK refuses nothing today.
Revisit if:   A refresh adopts nothing while FD keeps rejecting (pattern drift), or DK starts
              refusing "default-token" (then start on the JWT).
Where:        src/books/fanduel.ts (refreshKeys, readKeysFromBundle, isKeyRejection);
              src/books/draftkings.ts (onTokenRejected, renewJwt, DEFAULT_TOKEN);
              src/scripts/watch.ts (FD_APP_KEY, FD_PIR_KEY, DK_TOKEN_MODE); README "Cookies,
              tokens and sessions", DK-4, FD-15.

D-40  Synthetic books are one book across processes; the failure drills run on them
Status: Accepted 2026-10-19 | PDF: Goal; Key Concept 5 | Owner: Claude (build)
Context:      The drills, two-feed local runs and the load test need two feeds over one book, as
              Box A and Box B see one real book. Each fake process used to walk prices on its
              own, so a second feed was a different book lagging by its start time: the merge
              took its older prices as new (fresh book times) and the board flip-flopped.
              Breaking real books on purpose would risk the live board and our IPs' standing.
Decision:     - Fake prices are a pure function of (seed, book, wall-clock tick). Tick k changes
                one market, picked and priced by k's seeded draws around the market's opening
                (line +/- 0.5, fair probability +/- 3 points). Ticks fire on wall-clock
                multiples of 1000/FAKE_RATE ms and a late timer replays the ticks it missed. A
                process that starts late restores each market's latest change by looking back.
              - Book times keep the real resolutions: DK the tick - 40 ms, FD whole seconds on
                push, none on poll. Kickoffs hang off the UTC day. Misbehavior (fail, freeze,
                garbage, massRemove) stays per process.
              - scripts/drills.ts (npm run drills) starts a board and a feed process linked over
                TCP, breaks one thing at a time (crash, hang, a stopped book, a 2 s link lag via
                a delaying proxy, bad prices, a mass removal, a frozen feed) and times what
                /api/health, /api/board and the stream show.
Alternatives: - A shared walk behind a coordinator process: rejected; a service just for a fake.
              - Replaying a recording: kept for the merge tests (test/fixtures), but it is
                finite and FD-only; drills and local runs need both books indefinitely.
              - Drills against the real books in production: only the safe one (stopping Box B,
                D-25); CHAOS is refused in production.
Evidence:     test/fake.test.ts: a connector started 5 s later holds the same prices, then
              reports the same changes with the same book times (both books). Drills: 11 of 11
              pass after two fixes they prompted (D-25, D-35); README "The board".
Trade-offs:   Fake prices wander inside a band around each opening instead of drifting; a
              change reaches FD's push or poll channel, never both, so the board's push/poll
              race is only exercised by the live replay (D-35). Processes started on different
              UTC days disagree on kickoffs.
Revisit if:   A drill needs per-feed source lag or dropped frames (only link lag is modelled).
Where:        src/server/fake.ts, test/fake.test.ts, scripts/drills.ts, scripts/load-sse.ts;
              README "The board: two feeds, one view", "Running the app".
